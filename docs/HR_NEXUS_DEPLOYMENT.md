# HR Nexus on Vercel

How the deployed shape differs from the local one, and why it is shaped that
way. The local setup is unchanged: `backend/src/server.ts` still listens on a
port, Docker still provides Postgres, and nothing here affects either.

## The deployed shape

Two things are published, and only two:

| What | Where it comes from |
| --- | --- |
| The site | `frontend/dist`, built by `vercel.json`'s `buildCommand` |
| The API | `api/index.js`, a single serverless function, committed to the repository |

`vercel.json` routes between them. The filesystem is consulted first, so built
assets serve directly; the two rewrites then handle everything that did not
match a file:

- `/api/(.*)` → the function.
- `/((?!api/).*)` → `/index.html`, so that a deep link such as `/login` or
  `/people/org-chart` loads the application instead of returning 404. A
  single-page application has no file at those paths; without this rewrite only
  the site root works and every bookmark is broken.

## Why the API is a committed bundle

`api/index.js` is generated by esbuild from `backend/src/app.ts`, and it is
committed rather than built on the host. That is unusual enough to justify.

The API is bundled with its dependencies inlined and emitted as CommonJS, which
leaves the host nothing to decide. It does not have to install anything for the
API, resolve a single `import`, pick an entry point among candidates, or infer a
module format. Each of those decisions failed in a different way when the host
was making them, and the most stubborn failure is worth naming, because it will
look familiar if it ever returns:

```
/var/task/app.js: import cors from "cors";
SyntaxError: Cannot use import statement outside a module
```

`backend/package.json` declares `"type": "module"`, so the backend's own source
is ESM and correct. The deployed function root carries no such declaration, so
a `.js` file there is CommonJS, and ESM written into that filename cannot load.
A build that looks entirely successful then produces a function that cannot
start. Committing a `.cjs`-semantics bundle under a `.js` name in a directory
with no `"type"` removes the ambiguity rather than relying on the host to
resolve it correctly.

The cost is that the artifact is a build output under version control, and it
goes stale silently. **Whenever anything under `backend/src` changes, rebuild
it and commit the result:**

```bash
npm --prefix backend run build:api
```

`npm --prefix backend run build` does this too, after type-checking.

## Password hashing

The API uses `bcryptjs`, a pure-JavaScript implementation, rather than the
native `bcrypt`. Native `bcrypt` compiles through `node-gyp` at install time and
ships a binary that cannot be bundled, which is incompatible with a
self-contained function.

The two are interchangeable on the wire: both produce `$2b$` hashes at the same
cost factor, and each verifies hashes written by the other. Existing stored
hashes keep working and no password needs to be reset. `bcryptjs` is slower per
hash, which for sign-in is immaterial.

## Environment variables

Set in the Vercel dashboard, for Production and Preview:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | Hosted Postgres. The API refuses to start without it. |
| `JWT_SECRET` | Signs sign-in tokens. Never the local development value. |
| `JWT_EXPIRES_IN` | How long a sign-in lasts, for example `7d`. |
| `VITE_API_BASE_URL` | `/api`. Read at build time by the frontend. |

`.env.vercel.example` documents these in full, including the one-time setup
variables that are used from your own machine and never by the deployed server.

Profile photographs are off by default, because a serverless filesystem is
read-only: the API starts and refuses uploads with a 503 rather than failing to
boot. Setting `PROFILE_IMAGE_DIR=/tmp/profile-images` accepts them for the life
of one instance, after which they are gone. Durable photographs need object
storage, which is not yet wired up.

## Verifying a deployment

```bash
curl -s https://<deployment>/api/health          # {"success":true,...}
curl -s -o /dev/null -w '%{http_code}\n' https://<deployment>/login   # 200, not 404
```

If `/api/health` returns 500, read the function's runtime log and check the
filename in the stack trace. It should be `/var/task/api/index.js`. Any other
filename means the host built something of its own instead of serving the
committed function, which is the failure this layout exists to prevent.
